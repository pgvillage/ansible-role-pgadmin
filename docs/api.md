# pgAdmin web role

Deploys pgAdmin in server mode on hosts selected by the playbook, including a
management VM. It does not require PostgreSQL to be installed on the same host.

| Target | Installation | Application hosting | Runtime account |
| --- | --- | --- | --- |
| RHEL 9, 10 | `pgadmin4-web` RPM | Apache / mod_wsgi | `apache:apache` |
| Ubuntu 24.04, 26.04 | `pgadmin4-web` DEB | Apache / mod_wsgi | `www-data:www-data` |
| openSUSE Leap 16 | `pgadmin4` in a virtual environment | Gunicorn behind Apache | `wwwrun:www` |

No additional Linux user is created. Apache retains its distribution service
configuration. Gunicorn runs as the existing web service account, with one
worker and multiple threads, bound to `127.0.0.1` only. The Flask development
server is never used.

## Prerequisites

- Gather Ansible facts and run the role with root privileges (`become: true`).
- Install the `community.general` and `ansible.posix` collections.
- Run the Linux role first to configure repositories, signing keys and OS
  prerequisites for the hosts in the chosen inventory group. The upstream
  pgAdmin APT/RPM repository is separate from the PostgreSQL server repository.
  This role installs application packages but does not configure repositories.
- Repository installations use upstream x86_64 packages. Custom repositories can
  override `pgadmin_package_architectures` and `pgadmin_package_names`.
- On openSUSE Leap 16, Linux must provide Python 3.10 or newer with `venv` and
  `ensurepip`. For example, provision `python313`/`python313-pip`.
  Set `pgadmin_python_executable` to that
  interpreter if `/usr/bin/python3` is older. Dependencies must be available from
  the configured Python package index, including wheels for the target platform
  or the corresponding build dependencies. Python 3.13 is the local validation
  target for the pip path.
- Provision a valid server certificate/full chain and an unencrypted private key
  before this role runs. Certificates are managed by the certificate workflow,
  not generated by this role.
- Add TCP 443 for these hosts to the inventory's `firewall_ports`, and ensure
  the firewall play targets them. The role never installs or starts a firewall.
  With external TLS termination, allow only the required proxy-to-backend access.

## Example

```yaml
- name: Deploy the database administration interface
  hosts: pgadmin
  become: true
  gather_facts: true
  vars:
    pgadmin_server_name: pgadmin.example.org
    pgadmin_admin_email: database-admin@example.org
    pgadmin_admin_password: "{{ vault_pgadmin_admin_password }}"
    pgadmin_tls_certificate_file: /etc/ssl/certs/pgadmin-fullchain.pem
    pgadmin_tls_key_file: /etc/ssl/private/pgadmin.key
  roles:
    - pgvillage.pgadmin
```

The Linux and certificate prerequisites above must already have been applied to
the same hosts. The `pgadmin` inventory group can contain the management VM or
another server. Membership alone does not run the Linux or firewall play on it.

Browse to `https://pgadmin.example.org/pgadmin4/login`. The administrator account
is a pgAdmin web login, separate from PostgreSQL users and Linux accounts.

## Configuration

| Variable | Default / purpose |
| --- | --- |
| `pgadmin_install_method` | `pip` on openSUSE Leap 16, `package` on RHEL and Ubuntu |
| `pgadmin_package_names` | Platform application packages, Apache and ACL tools; includes `mod_ssl` on RHEL with HTTPS |
| `pgadmin_package_state` | `present`; optionally `latest` for repository packages |
| `pgadmin_admin_email`, `pgadmin_admin_password` | Required only for initial database creation; password must meet `PASSWORD_LENGTH_MIN`, with a minimum of eight characters |
| `pgadmin_server_name` | Host FQDN; set to the name in the server certificate |
| `pgadmin_url_path` | `/pgadmin4`; one or more URL path segments without a trailing slash |
| `pgadmin_tls_enabled` | `true`; requires certificate and key file paths |
| `pgadmin_webserver_address` | `*`; virtual host address on the distribution's existing listener |
| `pgadmin_webserver_port` | 443 with TLS, 80 otherwise; only the standard listeners are supported |
| `pgadmin_secure_cookies` | `true`; keep enabled when TLS terminates at an external proxy |
| `pgadmin_data_dir`, `pgadmin_log_dir` | `/var/lib/pgadmin`, `/var/log/pgadmin` |
| `pgadmin_config` | Additional uppercase pgAdmin settings, represented as native YAML values |
| `pgadmin_python_executable` | `/usr/bin/python3`; used to create the pip virtual environment |
| `pgadmin_virtualenv` | `/opt/pgadmin/venv`; root-owned application installation |
| `pgadmin_pip_version` | `9.19`; explicitly change to upgrade the Python application |
| `pgadmin_gunicorn_requirement` | `gunicorn>=25,<26`; installed with `state: present` |
| `pgadmin_gunicorn_port` | 5050; loopback backend port, never a public listener |
| `pgadmin_gunicorn_threads`, `pgadmin_gunicorn_timeout` | 25 threads, 300 seconds; worker count stays at one as required by pgAdmin |

The role manages `/etc/pgadmin/config_system.py`, the platform's pgAdmin Apache
configuration, and `/etc/systemd/system/pgadmin.service` for pip installations.
The system configuration directory is fixed at `/etc/pgadmin`. Installation
method changes on an already configured host are not supported; migrate it
deliberately rather than switching between package and pip in place.

For example:

```yaml
pgadmin_config:
  ALLOW_SAVE_PASSWORD: false
  PASSWORD_LENGTH_MIN: 12
  LOGIN_BANNER: 'Pgvillage database administration'
```

Settings are serialized as Python values; do not put Python expressions in the
dictionary. Server mode, runtime paths, URL mounting, secure cookies and proxy
trust settings are managed through the role variables and cannot be replaced
through `pgadmin_config`. Additional settings can contain secrets: use Vault.
Template diffs are suppressed for the application configuration.

For an existing TLS reverse proxy on the same host:

```yaml
pgadmin_tls_enabled: false
pgadmin_webserver_address: 127.0.0.1
pgadmin_secure_cookies: true
```

Have the proxy preserve the hostname and `/pgadmin4` path. The role's Apache
configuration replaces client-supplied proxy headers and advertises HTTPS when
secure cookies are enabled. For a private HTTP-only smoke test, also set
`pgadmin_secure_cookies: false`; otherwise browsers cannot retain the login cookie
over HTTP. Do not expose that test configuration as the customer endpoint.

On SELinux-enabled RHEL hosts, the role installs management dependencies, applies
file contexts to its configuration/data/log directories, and enables
`httpd_can_network_connect_db`. Nonstandard PostgreSQL/router ports must also be
labeled appropriately in the host's SELinux policy. SSH tunnels or connections
to other kinds of endpoints may require additional policy; SELinux is not disabled.

## Initialization and maintenance

Initial credentials are passed through the environment under `no_log`, never
written into a service unit or application configuration file. Changing them
after bootstrap does not reset the existing account. Subsequent runs can omit
the bootstrap password. Use pgAdmin's account administration for password changes.

Initialization and package upgrades run pgAdmin's `setup.py setup-db` as the web
service user. A read-only SQLite inspection distinguishes an initialized database
from a missing one. Nonempty corrupt/incomplete databases fail with a recovery
message instead of being deleted. Back up the data directory before application
upgrades; pgAdmin schema migrations are not a supported downgrade mechanism.

The success marker is written only after the login page and database checks pass.
It does not replace the database inspection, so a stale marker cannot conceal a
missing database. Configuration changes and package upgrades restart the relevant
services after Apache syntax validation. Services are enabled across reboots.

The default health check accesses the loopback HTTPS endpoint using the virtual
host's Host header. It does not verify a DNS certificate against `127.0.0.1`.
For certificate validation, set `pgadmin_healthcheck_url` to the DNS URL and
`pgadmin_healthcheck_validate_certs: true`, with the issuing CA trusted on the host.
The default check retries twelve times at five-second intervals.

Check mode performs prerequisite checks and predicts repository/package/directory
changes. It skips pip installation, application configuration, bootstrap and
service/HTTP operations, so it cannot prove a fresh deployment will converge.

Database server registrations are deliberately left to users for now. Connections
originate from the pgAdmin host: arrange DNS, routing, database firewall rules,
`pg_hba.conf` and client certificates accordingly. For pgAdmin backup/restore
features, provision matching PostgreSQL client utilities through Linux and
configure pgAdmin's binary paths as appropriate.

## Local validation

Run the SQLite bootstrap regression checks with:

```console
python3 -m unittest discover -s tests -v
ansible-lint --offline .
```

These do not install packages or start services. No Molecule scenarios are
included. Full OS installation, SELinux enforcement and reboot testing still
require representative target VMs.
